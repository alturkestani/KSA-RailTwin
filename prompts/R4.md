## Tasks
1. **Running-time model** (`isochrone-commute`): acceleration–cruise–brake plus dwell per stop (explicit minute cost per stop), parameters per rolling-stock class as registered assumptions with sources (manufacturer data sheets, published timetables); reproduce the Haramain Makkah–Jeddah published time within ±10 % as the validation gate (cite the timetable `S-nnn`); `uv run python -m access.running_time --line cities/ksa/lines/hhr.yaml --pattern all-stop --seed 1`.
2. **Isochrones**: 30/45/60-minute in-vehicle and door-to-door isochrones for every metro in the CP1 list, per scenario S0, S1 and each S2–S5 candidate; door-to-door uses access/egress from R1a skims plus the registered summer first/last-mile penalty; population and jobs reached per band from R3 zones. GeoJSON under `runs/access/<scenario>/`.
3. **The 30-minute test** (`access/commute_test.py`): for every town 40–120 km from each metro (from the register): can a train deliver about 30 minutes in-vehicle, and what door to door; the modelled car-trip reduction per the R3 mode-choice shares with the sensitivity band. `docs/commute-test.md`: a table per metro, labelled "synthetic demand, uncalibrated: scenario comparison, not a forecast"; write "in the model, car trips fell by X–Y %", never "will".
4. **Jeddah decongestion coupling** (`coupling/jeddah.py`): translate the modelled Jeddah-related rail shift (commuter belt and Haramain/trunk scenarios) into TrafficTwin policy YAML (TrafficTwin `policy-yaml` style, e.g. a `pt_line`/mode-shift transform with the shift shares from R3) and run TrafficTwin's matched-control procedure (`uv run python -m sim.runner --policy ... --daytype weekday --sample 0.10 --seed 1` executed from the TrafficTwin checkout with outputs redirected into `runs/coupling/`): VHT, delay, teleport share, seed band (seeds 1–3 if time allows; estimate first). Report deltas against the matched control, with the teleport share as the quality flag, as TrafficTwin's `docs/policies.md` does. If the disk gate blocks the runs, write the policy YAMLs, the exact commands and the estimate, and mark `pending disk`.
5. **Optional SUMO rail**: only if time and disk remain after task 4: a headway/capacity check of one trunk corridor with SUMO rail on a synthetic line; otherwise write the method and mark deferred.
6. **Corridor costs**: for every S2–S5 candidate, `uv run python -m costs.estimate` (R1c) with the corridor's terrain and structure shares → P10/P50/P90 capex and opex per candidate into `runs/costs/<id>/`; a summary table `runs/network-eval/<scenario>/summary.parquet` (one row per candidate: km, stations, running time, isochrone population reached, 30-minute towns, capex and opex ranges, run ids).
7. **Tests** on the fixture corridor and 6 zones: running-time determinism and the fixture's HHR-like check; isochrone population counts; commute-test table shape; coupling YAML validates against TrafficTwin's schema (import its pydantic models read-only).
8. **Docs and handoff**: `docs/network-evaluation.md` (method, per-scenario summaries with run ids, validation gate result), `docs/jeddah-coupling.md` (policy YAMLs, commands, results or estimate, teleport flags), registers; `make test`; `red-team-verifier`; commits per task; status block in `docs/status/r4.md` (validation gate result, isochrones per metro, 30-minute towns per metro with ranges, coupling runs with ids or the pending estimate, disk before/after). End with `R4: done` or `R4: blocked - <reason>`.
