## Tasks
1. **Objectives** (`objectives.py`), each read from run outputs, never recomputed by hand: maximise NPV and BCR (R5 P50 with the P10/P90 band carried along), coverage/equity (population and jobs reached within the 30/45/60-minute bands from R4; regional balance index defined and registered), emissions reduction (R5 stream); minimise fiscal exposure (R5 fiscal cost; R7 will refine) and risk (spread of the Monte Carlo draws). Write the exact definitions in `docs/optimisation.md`.
2. **Decision variables**: which corridors to build and their alignment options (from R2 candidates), station siting (p-median / coverage with a through-passenger time penalty from the R4 running-time model), technology per corridor (HSR, conventional, upgrade, mixed freight/passenger, with their R1c cost classes), service and stopping patterns (express, skip-stop, all-stop), frequencies and fare levels (within the R3 mode-choice sensitivity).
3. **Method**: choose NSGA-II (`pymoo`) or epsilon-constraint with OR-Tools/HiGHS/CBC and justify the choice in `docs/optimisation.md` (problem size, integrality, evaluation cost); implement the other as a cross-check on the fixture. `uv run python -m optimise.pareto run --envelope <SAR bn> --population-scenario <id> --seed 1 --generations N --out runs/optimise/<id>/` writes the Pareto archive (Parquet: decision vector, every objective with its band), trade-off charts (PNG, with the synthetic label), `meta.json`. Run per budget envelope from `optimise_envelopes.yaml` (each envelope sourced to a published fiscal reference or registered as an assumption).
4. **Siting** (`siting.py`): p-median / coverage model for station additions and commuter-belt stations with the through-passenger penalty; validated on the fixture (known optimum).
5. **Sequencing as real options** (`sequencing.py`): stage-gates (build, expand, defer) triggered by observed demand and population thresholds; evaluate the phased programmes under the R3 population scenarios and the R5/R1c uncertainty draws; report option value relative to a fixed programme. Triggers and thresholds are registered assumptions.
6. **Robustness** (`robustness.py`): how often each recommended programme stays within x % of the Pareto front across Monte Carlo draws and population scenarios (x registered); regret metrics; the dominated options with the reason each is dominated.
7. **Outputs**: `scenarios/S6-<envelope>-<model>.yaml` for each recommended programme (`scenario-yaml`, `kind: optimised_programme`, listing corridors, technology, patterns, phase years as stage-gate conditions, not promises); `docs/phasing.md` with the recommended phased programme per envelope, its robustness, and the explicit statement that phase timing is conditional on triggers; trade-off charts referenced by run id.
8. **Tests**: fixture problem with a known Pareto front (3 corridors, 2 objectives) solved by both methods within tolerance; siting optimum; sequencing determinism; all under 30 s.
9. **Handoff** (`milestone-handoff`): `make test`, `red-team-verifier` (objectives trace to run ids, no hand-set weights presented as results, ranges, registered triggers), commits per task, status block in `docs/status/r6.md` (envelopes run, front sizes, recommended programmes, robustness, elapsed, disk). Write the **CP5 decision list** (envelope set, preferred programme per envelope, triggers) into `docs/STATUS.md`. End with `R6: done` or `R6: blocked - <reason>`.

## Acceptance (the verifier checks these)
- Every objective value traces to an R4/R5 run id; no objective is recomputed outside those outputs.
- The method choice is justified and cross-checked on the fixture; the solver and its licence are registered.
- Pareto sets exist per envelope with trade-off charts; dominated options are listed with reasons.
- Phasing is expressed as stage-gates with registered triggers, evaluated under all population scenarios; robustness is reported with the x % definition.
- S6 scenarios validate; nothing is presented as a single-point optimum or a promise.
